# แผนนำเข้าข้อมูลปีการศึกษา 2569

เอกสารนี้เป็นแผนปฏิบัติงานสำหรับข้อมูลรายชื่อนักเรียนปัจจุบันและข้อมูลประวัติใบประกาศ
ยังไม่ใช่คำสั่งนำเข้าข้อมูลจริง

## ขอบเขตข้อมูล

- แหล่งประวัติ: Firebase ปัจจุบัน จำนวน 3,278 รายการ ใช้อ่านอย่างเดียว
- แหล่งรายชื่อปัจจุบัน: ไฟล์รายชื่อ ม.1–ม.6 ในโฟลเดอร์โครงการ
- ผล audit รอบล่าสุด: 6 ไฟล์, 16 worksheets ต่อไฟล์, 3,155 แถวที่อยู่ในขอบเขตนำเข้า
- ห้องที่นำเข้า: ม.1–ม.3 ห้อง 1–15 และ ม.4–ม.6 เฉพาะห้องที่มีอยู่จริงตามไฟล์
- ห้อง 16 และนักเรียนที่ออกแล้ว: ไม่อ่านเพื่อการนำเข้า ไม่จับคู่ และไม่สร้างรายงาน
- ครูที่ปรึกษา: อ่านจากส่วนหัวของแต่ละ worksheet รองรับหนึ่งหรือสองคน
- แบบแม่กองธรรม: ใช้ต้นฉบับตรี โท เอก แยกไฟล์และแยกช่องสอบ ไม่แก้โครงสร้างต้นฉบับ

## ผลตรวจ Firebase live รอบล่าสุด

อ่านจาก Realtime Database แบบ read-only ผ่าน anonymous session เมื่อ 13 กันยายน 2569 ได้ 3,278 รายการ, ไม่มีชื่อว่าง, ไม่มีเลขใบประกาศว่าง และไม่พบระดับที่ไม่รู้จัก สัดส่วนตามระดับคือ ตรี 1,933, โท 701 และเอก 644; แบ่งเป็นมัธยมศึกษา 3,227 และอุดมศึกษา 51 รายการ

เมื่อนำชื่อที่ normalize แล้วไปเทียบกับ roster ปัจจุบัน 3,155 คน ได้ผลระดับบุคคลดังนี้:

- จับคู่แบบชื่อไม่ซ้ำ: 837 คน
- พบหลายรายการ ต้องตรวจสอบ: 72 คน
- ยังไม่พบคู่: 2,246 คน

การวิเคราะห์กติกาชั้นบังคับแยกจากผลจับคู่พบว่า ม.1 มี 592 คน และ ม.4 มี 475 คน รวม 1,067 คนที่ต้องสมัครชั้นตรีตามนโยบาย แม้ไม่พบประวัติใน Firebase ก็ตาม ส่วนคำแนะนำจากประวัติแบบชื่อไม่ซ้ำพบผู้ที่มีแนวโน้มสมัครต่อชั้นโท 763 คน, ต่อชั้นเอก 17 คน และพบประวัติชั้นเอกแล้ว 36 คน ตัวเลขคำแนะนำเหล่านี้เป็นเพียงข้อมูลช่วยเจ้าหน้าที่ เพราะ Firebase เดิมไม่เก็บสาย ม.ต้น/ม.ปลาย และชื่อซ้ำ 72 คนยังต้อง review

ตัวเลขนี้เป็นผลเตรียม review ไม่ใช่การยืนยันสิทธิ์สมัคร และยังไม่ถูกเขียนเข้า Supabase จนกว่าจะมีเจ้าหน้าที่ตรวจและเปิด migration/import อย่างเป็นทางการ

สามารถสร้างสรุปแบบไม่พิมพ์ PII ซ้ำได้ด้วย `scripts/audit-progress-guidance.py` โดยส่ง snapshot Firebase และ `roster_staging.csv` ที่อยู่นอก repository

## ขั้นตอนตรวจสอบ

1. สร้าง `import_batches` สำหรับไฟล์แต่ละชุด พร้อมชื่อไฟล์ เวอร์ชัน และจำนวนแถว
2. ตรวจจำนวนห้องและจำนวนผู้เรียนกับสรุปของโรงเรียน
3. normalize ชื่อเพื่อสร้างผู้สมัครจับคู่กับ `legacy_certificates`
4. บันทึกผลเป็น `auto_matched`, `review` หรือ `unmatched` โดยไม่แก้แถว Firebase
5. ให้เจ้าหน้าที่ตรวจรายการชื่อซ้ำหรือความมั่นใจต่ำก่อนยืนยัน
6. จึงค่อยสร้างใบสมัครตามกฎสาย ม.ต้น ม.ปลาย และอุดมศึกษา

หลังนำเข้า `legacy_certificates` ให้ผู้ปฏิบัติงานที่ผ่านการยืนยันตัวตนเรียก
`refresh_certificate_matches_staff()` ได้หนึ่งครั้งหรือหลายครั้ง ผลลัพธ์ทำซ้ำได้โดยไม่สร้างคู่ซ้ำ
และแยกจำนวน `auto_matched`, `review_candidates` และ `unmatched_students` ให้ตรวจสอบก่อนยืนยัน

## เครื่องมือเตรียมผลจับคู่

ใช้ `scripts/build-match-review.py` เพื่อสร้าง CSV ผลจับคู่จาก snapshot ที่ได้รับการตรวจสอบแล้ว:

```text
python3 scripts/build-match-review.py <firebase-import.json> <roster_staging.csv> <output-outside-repository.csv>
```

เครื่องมือนี้อ่าน Firebase และรายชื่อปัจจุบันอย่างเดียว ไม่เขียนกลับ Firebase/Supabase
และผลลัพธ์มีข้อมูลส่วนบุคคลจึงต้องอยู่นอก repository การจับคู่แบบชื่อที่ตรงเพียงรายการเดียว
จึงเสนอเป็น `auto_matched`; ชื่อซ้ำจะเป็น `review`; ที่ไม่พบจะเป็น `unmatched`
เพื่อให้เจ้าหน้าที่ตรวจสอบก่อนนำเข้า `legacy_certificates` และ `certificate_matches` จริง

## การตรวจ snapshot Firebase

`scripts/audit-legacy-firebase.py` ใช้ตรวจจำนวนและการกระจายข้อมูลของ snapshot
โดยไม่พิมพ์ชื่อหรือเลขใบประกาศออกมา เนื่องจาก snapshot ใน workspace อาจเป็นคนละเวลา
กับฐานข้อมูล Firebase live จึงต้องตรวจ `records` และ `exam_years` ก่อนนำเข้าเสมอ
ห้ามใช้ตัวเลขจาก snapshot แทนจำนวน live ที่เจ้าหน้าที่ตรวจไว้แล้ว

ก่อนนำเข้า Supabase ให้ใช้ `scripts/build-legacy-import.py` แปลงเป็น CSV
โดยจะ normalize ชื่อ, ระดับ `ตรี/โท/เอก` และสาย `secondary/higher_education`
พร้อมเก็บ `source_payload` เดิมไว้เป็นหลักฐาน การแปลงนี้ยังไม่ใช่การเขียนฐานข้อมูล
และไฟล์ผลลัพธ์ต้องอยู่นอก repository เช่นเดียวกับไฟล์รายชื่อนักเรียน

หากต้องนำเข้าผ่าน SQL Editor ให้ใช้ `scripts/build-legacy-import-sql.py` สร้างไฟล์ SQL
จาก snapshot ที่ผ่าน validation แล้ว ไฟล์จะใช้ transaction และ upsert ด้วย `firebase_key`
พร้อมบันทึก `import_batches`; ต้อง review จำนวนแถวก่อนรันทุกครั้ง และห้ามนำไฟล์ SQL ที่มี PII เข้า Git

## กติกาสมัครเบื้องต้น

- ม.1 และ ม.4 ต้องมีรายการสมัครธรรมศึกษาชั้นตรี
- ม.ต้นและ ม.ปลายเป็นคนละสาย แม้เคยจบระดับสูงในอีกสายหนึ่ง
- การสอบต่อชั้นโทหรือเอกไม่บังคับโดยอัตโนมัติ
- ห้องสอบ เลขที่สอบ และผลสอบแสดงได้เมื่อมีไฟล์ประกาศทางการนำเข้าแล้วเท่านั้น

## ข้อห้าม

- ไม่ส่งไฟล์รายชื่อนักเรียนดิบขึ้น GitHub
- ไม่ใส่ service-role key หรือ Google credential ใน frontend หรือ repository
- ไม่เขียนข้อมูลเดียวกันกลับไป Firebase และ Supabase พร้อมกัน
- ไม่สร้างค่าห้องสอบ เลขที่สอบ หรือผลสอบขึ้นเอง
